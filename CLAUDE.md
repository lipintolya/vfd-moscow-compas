# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Site for the ВФД (Владимирская фабрика дверей) door & aluminum-partition showroom in **ТЦ «Компас», Moscow** (ул. Красная Сосна, 2А, 3 этаж). Forked from the Chelyabinsk site `vfd74.ru` (`~/Projects/vfd-door`, github.com/lipintolya/vfd74) — same architecture, separate brand layer, content and design. Astro 7 + Vue 3 islands + Tailwind v4, content and product data primarily in Russian. Statically built; deploy target not set up yet.

**Brand layer — never hardcode these in components:** domain, name, city (with case forms), address/coordinates, phones, email, socials, Metrika ID and section feature flags live in `src/config/site.ts` (`SITE`, `PHONE`). Legal entity/requisites/hours live in `src/lib/contacts-data.ts` (built from `SITE`). LocalBusiness JSON-LD comes from `src/lib/local-business-schema.ts` — don't hand-write it per page. `astro.config.mjs` duplicates the domain as `SITE_URL` (the config can't import TS) — change both (`robots.txt` and `/sitemap.xml` are generated from `SITE.url` by `src/pages/robots.txt.ts` and `src/pages/sitemap.xml.ts`). Values containing `PLACEHOLDER` / `placeholder.example` are unfilled real data — never invent real-looking replacements, ask the user.

**Reviews / hidden-door works** are empty for this salon; portfolio works come from Strapi (see «Strapi CMS» below). `SITE.features.{reviews,portfolio}` gates nav links, home sections, aggregateRating and noindex; `SITEMAP_EXCLUDE` in `astro.config.mjs` must be kept in sync. Never reuse Chelyabinsk objects/reviews as this salon's.

## Commands

```bash
npm run dev       # astro dev — local dev server
npm run build     # astro build — static build into dist/
npm run preview   # preview the production build locally
npm run gen:*     # image generators (scripts/*.mjs) — one npm alias per script, table in README «Облегчённые картинки»
npm run cms       # Strapi CMS (cms/) on localhost:1337 — must be running for dev/build (promos, portfolio)
npm run cms:install  # Strapi dependencies (first time / after upgrade)
npm test          # node:test via tsx — tests/*.test.ts (Strapi client and record mapping)
npm run deploy    # git push production main — no production remote yet; DO NOT run unless the user explicitly asks
```

Every `scripts/*.mjs` has an npm alias; a new generator gets one too (plus a README row). Generated files go to `public/renders/`; source images that exist nowhere else go to `assets/` (never `public/` — it ships to the site). `sharp` is a devDependency for these scripts.

After changing `src/content.config.ts`, restart `astro dev` — it keeps the old content store (a new article 404s and lists stay empty) until restarted.

Tests: `npm test` (node:test through `tsx`, `tests/*.test.ts`) covers the Strapi client and record → site-data mapping; no linter. `tsconfig.json` extends `astro/tsconfigs/strict`; rely on editor TS diagnostics for type issues, and `npm run build` as the main correctness gate (it runs `getStaticPaths` against the live Supabase project and reads Strapi, so a broken query or an unreachable Strapi fails the build). `node scripts/compare-builds.mjs <old dist> <new dist> [--only=/path/]` lists pages whose visible text changed — use it to prove a refactor or data move changed nothing.

## Strapi CMS

Strapi 5.57 lives in `cms/` (own `package.json`, TypeScript, SQLite locally in `cms/.tmp/`, uploads in `cms/public/uploads/` — both out of Git; versions pinned exactly). Content types are code: `cms/src/api/{promo,work,article}`, components `cms/src/components/{shared,article}`. On every start `cms/src/index.ts` bootstrap applies Russian field labels/hints (`bootstrap/labels.ts`), grants the Editor role (the director) full CRUD+publish on managed types (`bootstrap/access.ts` `MANAGED` — add a new content type there), registers the publish check (`bootstrap/publish-checks.ts`: on «Опубликовать» it reads the draft inside the publish transaction — the admin saves and publishes in one transaction, so the REST API would still show the old draft — and pipes it to `scripts/check-content.ts --stdin`, which runs `src/lib/content-checks.ts`: the build mapping `toArticle`/`toWork`/`toPromo` plus SEO rules — lead ≥70, an H2 and no H1 in text, every photo described, unique title, metaTitle ≤60; problems come back as a Russian ValidationError and nothing is published; `npm run check:content` checks everything published), and in dev creates the read-only API token «site-build» (upserting `STRAPI_URL`/`STRAPI_TOKEN` into the site `.env`) and a webhook to `http://localhost:4321/__strapi/refresh`. Admin UI is Russian by default (`cms/src/admin/app.tsx`); missing Strapi strings live in `cms/src/admin/translations/ru.json` — after upgrading Strapi run `npm --prefix cms run check:ru` (dictionary keys, strings hard-coded in Strapi code, broken ICU in Strapi's own ru). Photo descriptions fall back to the media library «Что на фото» (`alternativeText`) wherever the record's own alt is empty (articles; portfolio slider alts come only from it). Article «Страницы каталога» / «Серии каталога» are enum components: pages — `src/data/article-catalog-pages.ts` (test `cms-lists` keeps the Strapi enum and real `relatedArticle({ pagePath })` pages in sync), series — generated from Supabase by `npm run cms:series` (`checkArticleSeries` in the series page fails the build on an article with a vanished series and warns about catalog series missing from the list). Changing a component field's type needs a data move (the old rows stay linked under the old component type) — done once in SQL for pages/series. Strapi's ESM build doesn't load in plain Node — scripts load it via `createRequire` (`cms/scripts/import-works.mjs`, `import-articles.mjs` — one-off migrations, kept for reference).

Site side: `src/lib/strapi.ts` (`strapiFetchAll` — published only, all pages, Bearer token, clear errors; `strapiImage` — Strapi's resized copies as `src` + `srcset`, the original only if it's within the requested width) → `src/lib/strapi-content.ts` (`toPromo`/`toWork` map records to the old shapes; `strapiLoader` for `src/content.config.ts`) → pages use `getCollection('promos')` and `getWorks()` (`src/lib/works.ts`, newest first). Any Strapi error fails the build — never ship an empty section silently. Dev: `src/integrations/strapi-refresh.mjs` re-runs the Strapi loaders on the webhook (an edit shows up in ~1 s), and Vite proxies `/uploads` to Strapi; on the server nginx will serve `cms/public/uploads` at `/uploads` (stage 2: Strapi + Postgres on the VPS, rebuild on publish). The sitemap reads work photos from Strapi itself (`fetchWorkImages` in `astro.config.mjs`).

## Deployment — never run automatically

Deploy scripts in `deploy/` are templates carried over from vfd74 (domain = placeholder): a `post-receive` hook on a VPS checks out `main`, runs `npm ci && npm run build`, then `rsync`'s `dist/` to the nginx web root. There is no `production` remote yet. The GitHub remote is `origin` (github.com/lipintolya/vfd-moscow-compas). **Do not push to the `production` remote or run `npm run deploy` unless the user explicitly asks in that turn.** Default to local build/preview only.

## Architecture

**Rendering model**: Astro pages are server/build-time rendered (mostly static, with `getStaticPaths` for dynamic routes). Interactivity lives in Vue 3 "islands" mounted with explicit `client:*` directives (`client:only="vue"`, `client:load`, `client:visible`, `client:idle`) — pick the directive based on how critical-path the component is (e.g. `Header`/`Footer` use `client:only="vue"` to avoid hydration mismatches; below-the-fold sections use `client:visible`/`client:idle`).

**Data sources** — three distinct patterns, don't mix them up:
1. **Supabase-backed catalog** (`src/lib/supabase.ts`, requires `PUBLIC_SUPABASE_URL`/`PUBLIC_SUPABASE_ANON_KEY` in env): the main door catalog (`src/pages/catalog.astro`, `src/pages/models/[id].astro`) queries the `model_colors` table with nested joins to `colors → coatings` and `models → series → coatings`. Pages fetch all data server-side at build time, normalize into a flat `CardItem`/`CatalogCardItem` shape (one card per model, first color picked, hex colors normalized for a `С`/`C` Cyrillic-Latin typo seen in the DB), then hand the flat array to a Vue island (`CatalogClient.vue`) which owns all filtering/sorting/pagination/URL-query-sync client-side — there is no server round-trip for filtering.
   - Model pages and the Yandex product feed (`src/pages/feed/yandex.xml.ts` → `/feed/yandex.xml`, YML for Яндекс Товары) share one data source, `src/lib/model-entries.ts`, and one naming/description module, `src/lib/product-text.ts`. Yandex checks feed price/photos against the page, so change prices, photos or names there — never compute them separately in the page or the feed.
2. **Static TypeScript data modules** (`src/data/*.ts`): standalone product lines that aren't in Supabase yet — e.g. `skrytye-dveri-products.ts` (hidden/flush doors — sizes, pricing tiers, `calcCustomPrice`), `partitions.ts` (aluminum partitions), `door-categories.ts` (SEO landing-page content keyed by `slug`, rendered through the generic `DoorCategoryLanding.astro` template), `accessories.ts`, `series-descriptions.ts`. These pages are otherwise fully static/content-driven.
3. **Strapi CMS** (`cms/`, see «Strapi CMS» below): content the director edits — articles, promos and portfolio works. Read at build time into Astro collections `articles` / `promos` / `works`; components get the same shapes as before.

**Images**: every photo the site shows lives in the repo — `public/media/<bucket>/<path>` is a byte-identical mirror of the former Yandex Cloud buckets (`catalog-vfd`, `vfd74ru`, `vfd.moscow.compass`); code, data and articles reference `/media/…`, never `storage.yandexcloud.net` (only videos — `.mp4` in `videos.ts` and `partitions.ts` — stay in the cloud). Catalog data and prices stay in Supabase: its `model_colors.photo_url` still holds cloud URLs, and `localMedia()` (`src/lib/media.ts`, used in `catalog-data.ts`, `model-entries.ts`; the sitemap does the same in `astro.config.mjs`) swaps them for the local copy at build time; a missing copy falls back to the cloud URL with a `[media]` build warning — fix with `npm run media:pull` (downloads anything referenced but missing; `-- --check` lists it) and commit. og:image / twitter:image and every `/…` path inside JSON-LD are made absolute in `BaseLayout` (social networks and search engines need full URLs); the Yandex feed does the same for `<picture>`. Generators read sources through `scripts/lib/media.mjs` `loadMedia()` (local copy first, cloud only for originals that aren't on the site, e.g. full-size partition renders). A narrow exception is `public/renders/alum-covers/`, populated by `scripts/gen-render-gallery.mjs`: Astro's remote-image optimizer re-processes remote images on every dev request with no disk cache and mishandles aspect ratio for this particular gallery (see comment at the top of that script), so those renders are pre-resized with `sharp` and committed as local static files instead. Re-run `gen:renders` only if the partitions render count or the cloud originals change. Article, promo and portfolio photos live in the Strapi media library (`/uploads/…`) — Strapi makes the resized copies, the site builds `srcset` from them (`strapiImage`).

**SEO infrastructure** is load-bearing, not incidental:
- `BaseLayout.astro` centralizes `<head>` (OG/Twitter meta, canonical, favicons, JSON-LD via `structuredData` prop, font preloads, Yandex Metrika, the ФЗ-152 cookie-consent banner).
- `astro.config.mjs` wires `@astrojs/sitemap` with custom `serialize()`/`filter()` — priority/changefreq rules and `/privacy` exclusion are intentional, keep them when adding routes.
- **Articles** (`/articles/`): records of the Strapi type «Статьи» (`api::article.article`), read by `articlesLoader` into the `articles` collection; `toArticle` (`src/lib/strapi-content.ts`) maps a record to the old frontmatter-shaped fields plus `blocks`, `headings`, `cover` (SiteImage) and `body` (plain text for reading time/word count). Everything else is derived (`src/lib/articles.ts`): home block `LatestArticles`, the section, «статья по теме» on catalog pages (`RelatedArticleCard`; priority: `relatedPages` > `relatedCoatings` > `relatedSeriesSlugs` — the SEO group «Для поисковиков и каталога» in Strapi), sitemap with lastmod (`fetchStrapi('articles')` in `astro.config.mjs`), `/llms.txt`. Body = dynamic zone of `article.*` blocks (text as Strapi Blocks, photo, gallery 2–4 with «высокие двери», callout, video, table as `| … |` text, hidden-door prices, coating prices) → `toSiteBlocks` (`src/lib/article-blocks.ts`: HTML escaped, heading ids via github-slugger exactly like the former Markdoc, one slugger per article) → `ArticleBlocks.astro` renders them with the article components (Figure, PhotoGrid/Photo, Callout, InlineVideo, HiddenHeightPrices, CoatingPrices). Salon facts, prices, measure/install terms are substitutions `{адрес салона}`, `{цена комплекта Секрет}` … (names → `ARTICLE_VARS` paths in `src/data/article-substitutions.ts`, filled by `fillSubstitutions`, unknown name = build error naming the article) in text, lead, «Коротко», FAQ — never typed in; a new `ARTICLE_VARS` field needs a name there and a row in `docs/director-guide.md` (tests check both). Every article image is a `<button data-zoom={…}>` opened by `ArticleLightbox` — keep that wrapper. Author defaults to the founder from `SITE` (Person in BlogPosting); the SEO group «Автор» overrides it (e.g. a Telegram channel). SEO group «Показ на главной» (spotlight) puts the newest such article into the home `Spotlight` block. Article page and `/articles/` end with `ArticleNav` and the home `Videos` block. H2s as questions with the answer in the first lines. Cover: 16:9, 1920×1080, may carry a headline — shown uncropped.
- **Partner page `/partitions/oniks-alum/`** (ОНИКС ALUM partitions, collaboration with the salon): data and copy in `src/data/oniks-alum.ts` (facts from the factory site, rewritten — never paste their text verbatim; no prices — the factory publishes none), original photos in `assets/oniks-alum/` (README) → `npm run gen:oniks` → `public/renders/oniks-alum/`. The page centres on `OniksBuilder` (layout №1–10 × profile × glass → live SVG of the leaf; geometry and finishes in `oniks-alum.ts`, combination kept in `?layout=&profile=&glass=`; factory photos' «Собрать такую» fills it in). Material colours there are approximate — the page says so; don't present them as exact. All page copy lives in `oniks-alum.ts` (`ONIKS_HERO`, `ONIKS_SECTIONS`, `ONIKS_STEPS` → `StepsRow`…); factory numbers only in `ONIKS_SPEC` (texts, specs, FAQ, meta, `/llms.txt` derive from it), section counts derive from the layout geometry. The collaboration is stated in words in the hero lead — no «A × B» lockups, eyebrow pills or logos (and no ВФД logo next to the studio: ОНИКС is another factory); the page title names the studio, not ВФД. Linked from `/partitions/`, the footer, `/llms.txt`; sitemap priority 0.8.
- Landing pages under `/catalog/<slug>` follow the `DoorCategory` data shape in `door-categories.ts` + `DoorCategoryLanding.astro` template; adding a new SEO-targeted category landing page means adding a data object there, not a new bespoke `.astro` file, unless the page needs a real product grid (Supabase-backed) rather than static content.

**Styling**: Tailwind v4 is loaded via `@tailwindcss/vite` (no `tailwind.config.*`). All colors live in `src/styles/global.css`: brand scales in `@theme static` — `accent-*` = red #FF0020 (CTA, active states, «Новинка»), `secondary-*` = blue #1FA0D3 (text links via `text-secondary-700`/`--color-link`, focus rings, «В наличии»), `slate-*` = graphite neutrals (overrides Tailwind slate; `gray-*` is not used) — plus semantic tokens (`ink`, `body`, `link`, `graphite`, …). Never write hex/teal/gray in components; use these utilities or `var(--color-…)`. Exception: `<meta name=theme-color>` and webmanifest need literal hex. Page-specific CSS (e.g. `src/styles/partitions.css`) is imported directly by the page that needs it.

**Legal/company data**: `src/lib/contacts-data.ts` holds the salon info (address, hours, phones, payment methods — derived from `src/config/site.ts`) used across contacts, footer, privacy and structured data — update once, not per-component. For display use `address.postal` + `address.entrance` (two lines) or `SITE.address.full` (one line). The site owner is a private person: no legal-entity requisites are published (owner's decision); `ownerName` (for /privacy/) and the real `SITE.email` are still pending — `HAS_EMAIL` hides the placeholder address everywhere.

**Runtime conventions** (each fixes a bug that already happened):
- Modals/menus lock page scroll only via `useScrollLock()` (`src/lib/scroll-lock.ts`) — never `document.body.style.overflow`: `html` has `overflow-x: clip`, so body overflow does not reach the viewport and the page scrolled under open dialogs.
- `<Teleport>` inside a Vue island that is server-rendered (`client:load/visible/idle`) must be gated: `<Teleport v-if="mounted">` with `mounted` set in `onMounted`, otherwise hydration mismatches. `client:only` islands don't need it.
- `getCatalogCards()` / colors queries in `src/lib/catalog-data.ts` are memoized per build and throw on Supabase errors — a broken query must fail the build, never ship an empty catalog.
- Page-level `overflow-x` uses `clip`, not `hidden` (`hidden` breaks `position: sticky`).
