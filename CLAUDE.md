## Project

Site for the ВФД (Владимирская фабрика дверей) door & aluminum-partition showroom in **ТЦ «Компас», Moscow** (ул. Красная Сосна, 2А, 3 этаж). Forked from the Chelyabinsk site `vfd74.ru` (`~/Projects/vfd-door`, github.com/lipintolya/vfd74) — same architecture, separate brand layer, content and design. Astro 7 + Vue 3 islands + Tailwind v4, content and product data primarily in Russian. Statically built; deploy target not set up yet.

**Brand layer — never hardcode these in components:** domain, name, city (with case forms), address/coordinates, phones, email, socials, Metrika ID and section feature flags live in `src/config/site.ts` (`SITE`, `PHONE`). Map and route links come only from `src/lib/map-links.ts` (`MAP_URL` = the salon's Yandex Maps card `SITE.yandexMaps`, `ROUTE_URL` = route to it); writing to Konstantin — `src/lib/messengers.ts`: WhatsApp (`whatsappUrl()`, the phone with `whatsapp: true`) and personal Telegram (`telegramChatUrl()`, `SITE.social.telegramChat`), personal MAX (`maxChatUrl()`, `SITE.social.maxChat`; the link carries no text — MAX documents no parameter for it — so the message is copied on click via `data-copy-text`, `src/lib/copy-on-click.ts`); the MAX logo is the official symbol — `public/icons/max-dark.svg` on light backgrounds, `max-white.svg` on dark, rendered by `MaxIcon.vue` with `tone`, unchanged and without containers (the files are the official silhouette as one path — the original's mask/clip construction drew a black square in iOS Safari; same shape, verified pixel by pixel); the Telegram logo is the official plane — `public/icons/telegram-black.png` on light backgrounds, `telegram-white.png` on dark (PNG, transparent background), rendered by `TelegramIcon.vue` with `tone`; the WhatsApp logo likewise — `whatsapp-black.png` on light backgrounds, `whatsapp-white.png` on dark, via `WhatsAppIcon.vue` (messenger PNGs are 128 px and edge-to-edge like Telegram/MAX, so they line up at one size); one prefilled message `CONSULT_MESSAGE` («Здравствуйте, Константин! Пишу с сайта … — нужна ваша консультация.»), `*WithText(body)` for the calculator (`maxWithText(body)` for MAX); `SITE.social.telegram` is the read-only channel; `SITE.social.youtube` (+ `youtubeHandle`) is the YouTube channel — official logo `public/icons/youtube.svg` (`YOUTUBE_ICON` in `src/lib/messenger-icons.ts`, same on light and dark), shown in the footer, `/contacts/`, `/video/` (not in the header contacts popup — kept short on 13″ screens, owner asked; WhatsApp is not there either), the `Videos` block head, `sameAs` and `/llms.txt`. `SITE.social.vk` (+ `vkHandle`) is the VK community (`vk.ru/dveriziz`) — official logo `public/icons/vk.svg` (`VK_ICON`, blue rounded square with white glyph, same on light and dark), shown in the footer, header contacts, `/contacts/`, the plinth «Запросить цену» modal (`PlinthGrid`), `contacts-data` socials, `sameAs` and `/llms.txt`; empty `vk` hides it everywhere. LocalBusiness JSON-LD comes from `src/lib/local-business-schema.ts` — don't hand-write it per page. `astro.config.mjs` duplicates the domain as `SITE_URL` (the config can't import TS) — change both (`robots.txt` and `/sitemap.xml` are generated from `SITE.url` by `src/pages/robots.txt.ts` and `src/pages/sitemap.xml.ts`). Values containing `PLACEHOLDER` / `placeholder.example` are unfilled real data — never invent real-looking replacements, ask the user.

**Reviews** come from the salon's Yandex Maps card (`SITE.yandexMaps`) into `src/data/reviews.ts` — text as on the maps (only spacing around punctuation fixed), first name only (no surname or initial — ФЗ-152, decided by the owner), `YANDEX_RATING` as the card shows it; not carried over: the owner's own review, off-topic ones (furniture, entrance doors — not sold), ones naming another company («Дверизз»), ratings 1–3. ## Commands

```bash
npm run dev       # astro dev — local dev server
npm run build     # astro build — static build into dist/
npm run preview   # preview the production build locally
npm run gen:*     # image generators (scripts/*.mjs) — one npm alias per script, table in README «Облегчённые картинки»
npm run cms       # Strapi CMS (cms/) on localhost:1337 — must be running for dev/build (promos, portfolio)
npm run cms:install  # Strapi dependencies (first time / after upgrade)
npm test          # node:test via tsx — tests/*.test.ts (Strapi client and record mapping)
npm run deploy    # build + upload to https://dveriziz.ru (needs Strapi) — DO NOT run unless the user explicitly asks
```

Every `scripts/*.mjs` has an npm alias; a new generator gets one too (plus a README row). Generated files go to `public/renders/`; source images that exist nowhere else go to `assets/` (never `public/` — it ships to the site). `sharp` is a devDependency for these scripts.

After changing `src/content.config.ts`, restart `astro dev` — it keeps the old content store (a new article 404s and lists stay empty) until restarted.

Tests: `npm test` (node:test through `tsx`, `tests/*.test.ts`) covers the Strapi client and record → site-data mapping; no linter. `tsconfig.json` extends `astro/tsconfigs/strict`; rely on editor TS diagnostics for type issues, and `npm run build` as the main correctness gate (it runs `getStaticPaths` against the live Supabase project and reads Strapi, so a broken query or an unreachable Strapi fails the build). `node scripts/compare-builds.mjs <old dist> <new dist> [--only=/path/]` lists pages whose visible text changed — use it to prove a refactor or data move changed nothing.

## Strapi CMS

Strapi 5.57 lives in `cms/` (own `package.json`, TypeScript, SQLite locally in `cms/.tmp/`, uploads in `cms/public/uploads/` — both out of Git; versions pinned exactly). Content types are code: `cms/src/api/{promo,work,article}`, components `cms/src/components/{shared,article}`. On every start `cms/src/index.ts` bootstrap applies Russian field labels/hints (`bootstrap/labels.ts`), grants the Editor role (the director) full CRUD+publish on managed types (`bootstrap/access.ts` `MANAGED` — add a new content type there), registers the publish check (`bootstrap/publish-checks.ts`: on «Опубликовать» it reads the draft inside the publish transaction — the admin saves and publishes in one transaction, so the REST API would still show the old draft — and pipes it to `scripts/check-content.ts --stdin`, which runs `src/lib/content-checks.ts`: the build mapping `toArticle`/`toWork`/`toPromo` plus SEO rules — lead ≥70, an H2 and no H1 in text, every photo described, unique title, metaTitle ≤60; problems come back as a Russian ValidationError and nothing is published; `npm run check:content` checks everything published), and in dev creates the read-only API token «site-build» (upserting `STRAPI_URL`/`STRAPI_TOKEN` into the site `.env`) and a webhook to `http://localhost:4321/__strapi/refresh`. Admin UI is Russian by default (`cms/src/admin/app.tsx`); missing Strapi strings live in `cms/src/admin/translations/ru.json` — after upgrading Strapi run `npm --prefix cms run check:ru` (dictionary keys, strings hard-coded in Strapi code, broken ICU in Strapi's own ru). Photo descriptions fall back to the media library «Что на фото» (`alternativeText`) wherever the record's own alt is empty (articles; portfolio slider alts come only from it). Article «Страницы каталога» / «Серии каталога» are enum components: pages — `src/data/article-catalog-pages.ts` (test `cms-lists` keeps the Strapi enum and real `relatedArticle({ pagePath })` pages in sync), series — generated from Supabase by `npm run cms:series` (`checkArticleSeries` in the series page fails the build on an article with a vanished series and warns about catalog series missing from the list). Changing a component field's type needs a data move (the old rows stay linked under the old component type) — done once in SQL for pages/series. Strapi's ESM build doesn't load in plain Node — scripts load it via `createRequire` (`cms/scripts/import-works.mjs`, `import-articles.mjs` — one-off migrations, kept for reference).

Site side: `src/lib/strapi.ts` (`strapiFetchAll` — published only, all pages, Bearer token, clear errors; `strapiImage` — Strapi's resized copies as `src` + `srcset`, the original only if it's within the requested width) → `src/lib/strapi-content.ts` (`toPromo`/`toWork` map records to the old shapes; `strapiLoader` for `src/content.config.ts`) → pages use `getCollection('promos')` and `getWorks()` (`src/lib/works.ts`, newest first). Any Strapi error fails the build — never ship an empty section silently. Dev: `src/integrations/strapi-refresh.mjs` re-runs the Strapi loaders on the webhook (an edit shows up in ~1 s), and Vite proxies `/uploads` to Strapi; on the server nginx will serve `cms/public/uploads` at `/uploads` (stage 2: Strapi + Postgres on the VPS, rebuild on publish). The sitemap reads work photos from Strapi itself (`fetchWorkImages` in `astro.config.mjs`).

## Deployment — never run automatically

Production: **https://dveriziz.ru** on a FirstVDS VPS (Ubuntu 24.04, 1 GB; host in the local, git-ignored `deploy/server.json` — the repo is public; template `deploy/server.example.json`). The server runs nginx only — the site is built locally (the build needs Strapi) and uploaded as files: `npm run deploy` (`scripts/deploy-site.mjs`: `npm run build` → checks — every sitemap URL exists in `dist/`, `robots.txt` is the production one and not the demo's `Disallow: /`, no placeholder domain in HTML, `SITE_URL` matches the server domain → `rsync --delete` of `dist/` and `cms/public/uploads/` → `/uploads/` → pages whose *content* changed (hash of text/title/meta/JSON-LD/images, not asset names — `pageContent`) get that date as sitemap `<lastmod>` before upload and are sent to IndexNow after it (Yandex, Bing; `scripts/lib/indexnow.mjs`, key `SITE.indexNowKey`, key file `src/pages/[indexnow].txt.ts`, state `deploy/indexnow-state.json` git-ignored; manual `npm run indexnow`); macOS ships openrsync, so no `--chmod`). Server config is code: `deploy/setup-server.sh` (idempotent; `npm run server:setup`, `-- --cert` issues the Let's Encrypt certificate via webroot) and `deploy/nginx/` (`headers.conf` security headers + CSP — add any new external host there; `site.conf` caching/gzip/404; `dveriziz.ru.conf` https-only with www/http → 301 and HSTS; nginx 1.24 needs `listen … ssl http2`, not `http2 on`). Strapi runs only on the developer's machine for now — its SQLite and uploads exist only there (back them up); Strapi on the server (2 GB VPS, PostgreSQL, rebuild on publish) is the next stage. **Do not run `npm run deploy` or `npm run server:setup` unless the user explicitly asks in that turn.** The GitHub remote is `origin` (github.com/lipintolya/vfd-moscow-compas).

## Architecture

**Rendering model**: Astro pages are server/build-time rendered (mostly static, with `getStaticPaths` for dynamic routes). Interactivity lives in Vue 3 "islands" mounted with explicit `client:*` directives (`client:only="vue"`, `client:load`, `client:visible`, `client:idle`) — pick the directive based on how critical-path the component is (e.g. `Header` uses `client:only="vue"` — it reads the clock, the path and a `<Teleport>`, which would mismatch on hydration; below-the-fold sections use `client:visible`/`client:idle`). **`Footer` is `client:load` on purpose**: it is the only site-wide navigation present in the static HTML (the header's dropdown items exist only after a hover and only in the browser), so the section links on every page (catalog, hidden doors, wall panels, partitions, decor and the SEO landings) must live in `Footer.vue` — a link added only to `Header.vue` is invisible to a robot that doesn't run JS. Keep the Footer free of anything that differs between server and browser (clock, `window`, `<Teleport>` without a `mounted` gate).

**Data sources** — three distinct patterns, don't mix them up:
1. **Supabase-backed catalog** (`src/lib/supabase.ts`, requires `PUBLIC_SUPABASE_URL`/`PUBLIC_SUPABASE_ANON_KEY` in env): the main door catalog (`src/pages/catalog.astro`, `src/pages/models/[id].astro`) queries the `model_colors` table with nested joins to `colors → coatings` and `models → series → coatings`. Pages fetch all data server-side at build time, normalize into a flat `CardItem`/`CatalogCardItem` shape (one card per model, first color picked, hex colors normalized for a `С`/`C` Cyrillic-Latin typo seen in the DB), then hand the flat array to a Vue island (`CatalogClient.vue`) which owns all filtering/sorting/pagination/URL-query-sync client-side — there is no server round-trip for filtering. The filter/sort/count logic is pure functions in `src/lib/catalog-filter.ts` (tested); default order «Популярные» = `LEAD_SERIES_SLUGS` first («Урбан Древесный», the salon's call), then `POPULAR_SERIES_SLUGS`, then by price (`src/lib/popular-series.ts`); coating order = `COATING_ORDER`. Filters are multi-select checkboxes (price ranges `PRICE_BUCKETS`, series, colour, glass) kept in the URL (`?coating=&series=a,b&color=white&price=&glass=`; old `?color=<colour name>` and `?glass=1` links still parse); the colour filter works by colour families (`src/data/color-families.ts`, by words in the colour name, wood light/dark by tone) because Supabase colour names are per coating («Белый», «Эмалекс белый», «Эмаль белая»). Catalog components (`CatalogClient`, `CatalogGrid`, `CatalogProductCard`) are styled in the site design system (`src/styles/home.css`, `.h-*` tokens) and need a `.home` ancestor plus the `home.css` import on the page — landings and the series page wrap them that way.
   - Model pages and the Yandex product feed (`src/pages/feed/yandex.xml.ts` → `/feed/yandex.xml`, YML for Яндекс Товары) share one data source, `src/lib/model-entries.ts`, and one naming/description module, `src/lib/product-text.ts`. Yandex checks feed price/photos against the page, so change prices, photos or names there — never compute them separately in the page or the feed.
2. **Static TypeScript data modules** (`src/data/*.ts`): standalone product lines that aren't in Supabase yet — e.g. `skrytye-dveri-products.ts` (hidden/flush doors — sizes, pricing tiers, `calcCustomPrice`), `partitions.ts` (aluminum partitions), `door-categories.ts` (SEO landing-page content keyed by `slug`, rendered through the generic `DoorCategoryLanding.astro` template), `accessories.ts`, `series-descriptions.ts`; decor — prices/sizes in `decor-products.ts`, copy/FAQ in `decor-page.ts`, one category = `DecorSection.astro` (all three on `/catalog/decor/`, plinth on model pages via `PlinthSection.astro`). Plinth `/catalog/plintus/` = floor MDF profiles (`plintus.ts`, `PlinthGrid`) + lines LED / hidden / micro / veneer (`plintus-lines.ts`, `PlintusLine.astro`; photos `assets/plintus-lines/` → `npm run gen:plintus-lines`, which also makes 480 px copies of the floor photos). The supplier's assortment and photos are agreed, but neither the manufacturer's name nor its model names (US states) appear on the site; LED photos are numbered by the floor profile they share; prices stay «по запросу». Product + AggregateOffer JSON-LD — `productSchema()` (`src/lib/product-schema.ts`), never hand-written per page. Hidden-door prices on `/catalog/skrytye-dveri/` are a calculator (`HiddenPriceBuilder.astro`) over pure functions in `src/lib/hidden-door-price.ts` — tests (`tests/hidden-door-price.test.ts`) pin every number of the price list; change prices only in `skrytye-dveri-products.ts`, edge colours/series names there too (`HIDDEN_EDGES`, `HIDDEN_SERIES`). These pages are otherwise fully static/content-driven.
3. **Strapi CMS** (`cms/`, see «Strapi CMS» below): content the director edits — articles, promos and portfolio works. Read at build time into Astro collections `articles` / `promos` / `works`; components get the same shapes as before.

**Images**: every photo the site shows lives in the repo — `public/media/<bucket>/<path>` is a byte-identical mirror of the former Yandex Cloud buckets (`catalog-vfd`, `vfd74ru`, `vfd.moscow.compass`); code, data and articles reference `/media/…`, never `storage.yandexcloud.net` (videos — `.mp4` in `videos.ts` and `partitions.ts` — stay in the cloud, except the compressed club video in `public/renders/home/videos/`, see `videos.ts`). Catalog data and prices stay in Supabase: its `model_colors.photo_url` still holds cloud URLs, and `localMedia()` (`src/lib/media.ts`, used in `catalog-data.ts`, `model-entries.ts`; the sitemap does the same in `astro.config.mjs`) swaps them for the local copy at build time; a missing copy falls back to the cloud URL with a `[media]` build warning — fix with `npm run media:pull` (downloads anything referenced but missing; `-- --check` lists it) and commit. og:image / twitter:image and every `/…` path inside JSON-LD are made absolute in `BaseLayout` (social networks and search engines need full URLs); the Yandex feed does the same for `<picture>`. Generators read sources through `scripts/lib/media.mjs` `loadMedia()` (local copy first, cloud only for originals that aren't on the site, e.g. full-size partition renders). A narrow exception is `public/renders/alum-covers/`, populated by `scripts/gen-render-gallery.mjs`: Astro's remote-image optimizer re-processes remote images on every dev request with no disk cache and mishandles aspect ratio for this particular gallery (see comment at the top of that script), so those renders are pre-resized with `sharp` and committed as local static files instead. Re-run `gen:renders` only if the partitions render count or the cloud originals change. Article, promo and portfolio photos live in the Strapi media library (`/uploads/…`) — Strapi makes the resized copies, the site builds `srcset` from them (`strapiImage`).

**SEO infrastructure** is load-bearing, not incidental:
- **Title length**: model titles are built by `productTitle` with `fitPhrase` (`src/lib/product-text.ts`): type, brand, trim/edge always, coating and «в Москве» while the title fits `TITLE_MAX` (75 with the studio suffix); descriptions by `productMetaDescription` (≤ `DESCRIPTION_MAX` 158). Each model's title must be unique — the trim is what tells SKUs apart (test: `tests/seo-title.test.ts`).
- **Titles and brand**: every `<title>` is `brandTitle(base)` (`src/lib/seo-title.ts`) → «… | Студия Зизевского» — the salon name exactly as on its Yandex Maps card; the door brand ВФД goes into the base where it is the product brand («Двери ПЭТ ВФД в Москве — купить, цены»; models via `productName(m, { withBrand: true })`). Exception: `/reviews/` puts «Студия Зизевского» first. Query split (no cannibalisation): the home page targets «салон / магазин дверей в Москве» (title «Салон дверей в Москве: межкомнатные и скрытые двери ВФД | Студия Зизевского», H1 «Салон дверей ВФД в Москве», description with the catalog count and «от» price), `/catalog/` targets «купить межкомнатные двери в Москве», each landing its own query (coating / colour / style / glass); the brand query is carried by the title suffix, site name and Yandex/Google cards. The home Directions block links every landing (`DOOR_` / `COLOR_` / `STYLE_CATEGORIES`) with its H1 as the anchor. Style landings may select by `glass: true` (`/catalog/dveri-so-steklom/`); colour «под дерево» — `/catalog/dveri-pod-derevo/`. Strapi «Заголовок для поисковиков» is the base only — the publish check rejects a manual «| …». Site name for search engines: `og:site_name`, `application-name` and the home `WebSite` JSON-LD (`websiteSchema()`) = `SITE.studioName`; the `Store` JSON-LD `name` = `SITE.studioName`, `alternateName` = `SITE.fullName`, `brand` = ВФД. No district (СВАО) in titles/meta — «в Москве».
- `BaseLayout.astro` centralizes `<head>` (OG/Twitter meta, canonical, favicons, JSON-LD via `structuredData` prop, font preloads); Yandex Metrika and the ФЗ-152 consent banner live in `components/analytics/CookieConsent.astro` — Metrika loads only after «Принять», «Отказаться» is an equal button, footer «Настройки cookie» reopens it; logic in `src/lib/cookie-consent.ts`, facts for `/privacy/` and the separate consent document `/consent/` in `src/data/personal-data.ts` (bump `CONSENT_VERSION` when the consent terms change). No Metrika ID → no cookies, no banner.
- `astro.config.mjs` wires `@astrojs/sitemap` with custom `serialize()`/`filter()` — priority/changefreq rules and `/privacy` exclusion are intentional, keep them when adding routes. After it, `src/integrations/image-sitemap.mjs` adds every page's photos that have a non-empty `alt` to `sitemap-0.xml` (each photo once, on the first page it appears) — so photos reach Google Images; decorative images keep `alt=""` and stay out. Photos of the salon/mall/founder carry «Студия Зизевского» in `alt` (image search by the studio name).

**Runtime conventions** (each fixes a bug that already happened):
- Modals/menus lock page scroll only via `useScrollLock()` (`src/lib/scroll-lock.ts`) — never `document.body.style.overflow`: `html` has `overflow-x: clip`, so body overflow does not reach the viewport and the page scrolled under open dialogs.
- `<Teleport>` inside a Vue island that is server-rendered (`client:load/visible/idle`) must be gated: `<Teleport v-if="mounted">` with `mounted` set in `onMounted`, otherwise hydration mismatches. `client:only` islands don't need it.
- `getCatalogCards()` / colors queries in `src/lib/catalog-data.ts` are memoized per build and throw on Supabase errors — a broken query must fail the build, never ship an empty catalog.
- Page-level `overflow-x` uses `clip`, not `hidden` (`hidden` breaks `position: sticky`).
